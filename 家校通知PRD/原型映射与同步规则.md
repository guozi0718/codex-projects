#### 3. 对应原则

1. Web 端主菜单、页签和页面框架由各自基线项目管理；通知页面由“校务管理→家校通知”菜单进入。
2. PRD 固定链接应指向本次固定版本；PRD 里的字段、默认值、操作顺序、校验结果和异常表现需要与对应页面一致。
3. 学校 Web 为两步发布；代理商 Web 和运营后台为三步发布，先选学校，再填写通知内容，最后设置发布对象和发送方式。
4. 用户明确确认的规则不能被页面演示数据取代；尚未确认的规则留在 PRD 的待确认章节，不得写成已确定规则。
5. 小程序资料与模板本轮保持原样；不能用 Web 发布包替代小程序页面。
6. 客服管理项目只作为 PRD 章节框架和详细程度的写作参考，不把客服管理业务规则带入家校通知。

#### 4. 原型或需求变化后的同步步骤

1. 先识别变化影响的端、页面、字段和业务规则。
2. 更新本地原型，并以新固定版本保留旧发布版。
3. 同步更新对应端 PRD；跨端共用规则变化时同步更新全端共通规则。
4. 更新相关页面截图，或明确标记旧截图为历史参考，避免用旧图说明新版页面。
5. 更新固定版本链接、主菜单链接、版本登记、交付索引和核对记录。
6. 逐项核对原型是否有对应 PRD 说明；每条已确认的 PRD 操作、校验和异常是否能在对应页面找到。
7. 未确认问题继续标为待确认；用户确认后再移入已确认规则，并修改受影响的原型和文档。

#### 6. 未确认规则

编辑后有效期的准确重算时点、已设截止时间如何与重算并用、编辑后是否重新接纳既有或新增对象，仍按 Q66–Q68 待确认。全年级范围之后新建的班级是否加入为 Q70；代发人员改变目标学校后如何处理已填写的内容和对象为 Q71。见[全端共通规则第9节](家校通知一期产品需求文档-全端共通规则.md)。

原型用于页面与交互评审，不表示真实学校名单、后台归档、消息提醒服务或 PDF 文件生成已经上线。

全端业务口径以[全端共通规则](家校通知一期产品需求文档-全端共通规则.md)为主，各端 PRD 记录端特有差异。菜单页负责基线导航与页签，家校通知 V20 页面作为对应菜单内容挂载；运营后台使用版本目录内的 `dependencies/notice/` 静态包。三端发布包中 V20 的 `index.html`、`app.js`、`core.js`、`styles.css` 均与本地 V20 功能源 Git blob SHA-1 一致。完整固定链接、Git 提交、哈希和页面验证状态见[原型发布登记](原型发布登记.json)。当前 GitHub Pages 是评审原型，不代表生产环境。

#### 2. 对应原则

1. Web 的主菜单、页签、页面框架和路由归对应基线项目管理；家校通知页面需从对应项目菜单打开。PRD 不把独立通知模块预览页当成菜单基线。
2. Web PRD 中的“固定发布版本”链接必须与该 PRD 所描述的页面和截图属于同一发布版本。稳定链接只作快捷入口，不能代替固定版本引用。
3. 学校 Web 为两步发布；代理商 Web、运营后台因代学校发布而包含选学校步骤，共三步。每端 PRD 按该端实际流程维护。
4. 当前教师、家长小程序原型和模板仅本地留存。小程序截图为用户提供的视觉参考；不可标记为已发布原型或用 Web 版本替代。
5. 需求变更、交互现状和服务端待实现能力分开记录。待确认问题保留待确认状态；不得把建议或静态演示数据改写成定版规则/生产能力。

#### 3. 原型变更后的文档同步步骤

每次修改并发布原型时，按以下顺序完成对应更新：

1. **确定受影响端与功能源。** 检查学校、代理商、运营后台的基线菜单/框架，以及 V20 家校通知功能模块是否变化；明确修改是视觉、交互、字段还是业务逻辑。
2. **发布可复核版本。** 为受影响端保留不可变发布路径和 Git 提交号；不要只更新会漂移的稳定入口。若改变了共同业务规则，记录所有受影响端。
3. **同步 PRD。** 更新受影响端 PRD 的流程、字段、校验、异常与恢复、验收场景和“原型/实现边界”；共同规则变化同时更新全端共通规则。原型变化仅为视觉时，也更新对应截图和原型现状说明。
4. **同步证据。** 用新发布版本重新采集对应页面截图，写明采集日期、尺寸和提交；替换旧图时保留版本记录，禁止把旧图说成新版本截图。
5. **同步映射与索引。** 更新本文、`原型发布登记.json` 和 `PRD交付索引.md` 中的版本、基线、链接、提交号、哈希、端到端文档映射及待确认项状态。
6. **相互复核再提交。** 检查 PRD 链接/截图是否指向此次原型，原型所表达的页面是否在 PRD 中有对应页面/场景；将原型与 PRD 作为同一需求变更交付，使用同一任务编号，连续提交时在登记中记录两边提交号。

如果变更涉及未确认业务规则，先继续保留为待确认问题并标记受影响页面；用户确认后再同步为确定需求。视觉调整不可自行改变业务含义。
